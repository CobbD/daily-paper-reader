# ABSTRACT 

Modern Computer Use Agents (CUAs) directly interact with graphical user interfaces and execute third-party web tools, exposing them to indirect prompt injection across every rendered page and tool response. While the Dual-LLM pattern is the primary system-level architecture offering formal security guarantees – using an isolated Planner LLM (P-LLM) to fix execution paths before processing untrusted inputs via a Quarantined LLM (Q-LLM) – these guarantees break down in graphical environments. Because CUA interaction is inherently dynamic, plans cannot remain data-independent; they must branch based on anticipated runtime web content – covering all possible cases the agent may encounter. This exposes agents to branch steering attacks, where an adversary crafts untrusted data to coerce a CUA down a hazardous, pre-approved branch without injecting explicit instructions. We systematically study branch steering attacks and introduce STEER-Bench (101 tasks across 9 domains), showing high attack success against both standard (94.4%) and vanilla Dual-LLM (89.5%) CUAs. We then propose COBRA , an architecture that pairs trusted branching plans with ahead-of-time capability constraints, strictly bounding the parameters and destinations each branch may execute. On STEER-Bench, COBRA reduces attack success to 0% while retaining 97% benign utility. 1

# 1 Introduction 

Computer-use agents (CUAs) carry out natural language tasks by interpreting on-screen visual content and executing mouse and keyboard actions. Most CUAs follow a ReAct-style loop in which a single model repeatedly observes the environment, reasons over it, and selects the next action; increasingly, agents also invoke Model Context Protocol (MCP) tools exposed by website vendors, giving them direct access to backend capabilities alongside the graphical user interface (GUI). This architecture makes CUAs acutely vulnerable to indirect prompt injection (IPI) across two surfaces. The first is 

rendered web content – because a model processes both the user’s trusted request and untrusted web pages, documents, and messages, untrusted text can become indistinguishable from instructions within the shared context (Greshake et al., 2023; Debenedetti et al., 2024; Zhang et al., 2025b; Aichberger et al., 2025; Chen et al., 2025). The second is the 

MCP interface , where a malicious server can embed instructions in tool descriptions ( tool poisoning ), register tools that impersonate approved endpoints ( tool shadowing ), or alter tool behavior post-approval (Beurer-Kellner & Fischer, 2025). Unlike webpage content, MCP tool descriptions may be presented to the agent during initialization, before it visits any website. Crucially, these two surfaces can be composed: a CUA task may interleave GUI actions with MCP invocations, injected page text can steer external tool calls, and poisoned tool responses can hijack GUI behavior. Defending either channel in isolation leaves the composite system vulnerable. The Dual-LLM architecture mitigates IPI by strictly separating trusted planning from untrusted interaction (Willison, 2023; Debenedetti et al., 2026). A privileged planner (P-LLM) derives the entire execution sequence in advance from the

This yields control-flow integrity (CFI): every action the agent executes must follow a pre-authorized plan. While CFI provides robust security for structured tool-use agents whose parameters and sequences can be fixed a priori (e.g., scheduling a meeting across known calendar APIs), it fundamentally breaks down in dynamic CUA environments. Because web layout and state cannot be known before a page renders, control flow is tightly interleaved with runtime data. Plans must therefore incorporate branches over anticipated runtime states (Foerster et al., 2026). Under branching execution, an adversary can manipulate untrusted page content to drive the agent down a hazardous, pre-approved path without injecting novel instructions, an exploit known as a branch steering attack (Foerster et al., 2026). Branch steering demonstrates that CFI alone is insufficient for CUAs: agents additionally require data-flow integrity 

(DFI). That is, untrusted data must not manipulate which branch is taken, nor determine the critical parameters its actions receive. Enforcing DFI is uniquely challenging in CUAs because graphical primitives carry no intrinsic semantics: the same mouse click may open an innocuous tab or confirm an irreversible wire transfer, and static plans cannot differentiate between them. A standard Dual-LLM architecture bounds an agent to authorized action paths, but leaves this runtime data-flow channel unprotected. To address this challenge, we present COBRA , a system-level defense enforcing both CFI and DFI for CUAs. COBRA eliminates branch steering by constraining, ahead of time, the capabilities each branch may exercise (e.g., allowed destination domains, endpoints, and tool parameters). As illustrated in Figure 1, before observing any untrusted runtime data, the P-LLM compiles the user’s request along with approved site and tool metadata into an executable program annotated with branch-level constraints. A deterministic interpreter executes this program, querying a quarantined vision-language model (Q-VLM) strictly for visual perception. Because Q-VLM outputs remain untrusted, a central 

Branch Resolution Hub (BRH) dynamically validates branch conditions and action parameters against the plan’s constraints before execution proceeds. Deterministic HTTP and MCP proxy enforcers then intercept and police all external operations at the network boundary. By unifying GUI-mediated web traffic and MCP tool calls under identical constraint contracts, COBRA secures both injection channels even across deeply nested branches. In this paper, we make the following contributions : • Benchmarking Branch Steering: We introduce STEER-Bench , the first systematic benchmark designed to evaluate branch steering attacks in CUAs, spanning 101 end-to-end tasks across 9 real-world domains. We show that branch steering achieves an attack success rate (ASR) of 94.4% against standard CUAs and 89.5% against vanilla Dual-LLM systems. • System-Level Defense Architecture: We frame branch steering as a data-flow integrity failure and introduce 

COBRA , a dual-LLM framework that enforces ahead-of-time, branch-level capability constraints across both GUI-driven HTTP requests and MCP tool boundaries. • Empirical Evaluation: Across STEER-Bench, COBRA ( gpt-5 P-LLM and UI-TARS-1.5-7B Q-LLM) eliminates branch steering (0% ASR) while preserving 97% of clean-task utility. Furthermore, across four published CUA and MCP security benchmarks comprising 1,312 attacks, COBRA achieves 0% ASR on all the 1,259 attacks that fall within its threat model while maintaining 100% benign completion and 79% completion under active attack. 

# 2 Related Work 

Probabilistic defenses for CUAs. Malicious pop-ups, adversarial image patches, and visible or hidden visual prompt injections can manipulate CUAs (Zhang et al., 2025b; Aichberger et al., 2025; Chen et al., 2025). Detection-based defenses identify such threats from agent observations or actions (Yang et al., 2025; Hu et al., 2025), but depend on a model or classifier recognizing the attack. MELON detects indirect prompt injections in tool-use agents by rerunning the agent with the user’s request masked and comparing the resulting tool calls with those from the original run (Zhu et al., 2025). This approach is difficult to apply to live CUAs because clicks and keystrokes reveal little about the intended task, and the desktop environment cannot generally be reproduced exactly. 

Structural system-level defenses. Structural defenses instead enforce predefined properties independently of un-trusted content, and COBRA follows this approach. Dual-LLM architectures separate trusted planning from interaction with untrusted content (Willison, 2023). Later systems enforce executable plans, track data provenance or dependencies, or isolate components in tool-use and multi-agent systems (Debenedetti et al., 2026; Costa et al., 2025; Zhong et al., 2025; Abdelnabi et al., 2026; Wu et al., 2025). MCP security. Prior work characterizes attacks against MCP tool definitions and behavior (Beurer-Kellner & Fischer, 2025). MCPTox (Wang et al., 2026) and MCPSecBench (Yang et al., 2026) evaluate tool poisoning and post-approval manipulation, while ETDI (Bhatt et al., 2025) authenticates tool definitions and binds them to authorization decisions. These works primarily study MCP as a standalone interface; COBRA protects tasks combining MCP calls and web interaction. 

Evaluation methodology. WASP (Evtimov et al., 2025) evaluates web prompt injections that redirect agent actions, while OS-Harm (Kuntz et al., 2025) includes OS-level attempts to induce unauthorized behavior. MCP benchmarks instead focus on the tool interface (Wang et al., 2026; Yang et al., 2026; Zong et al., 2026). InjecAgent and ASB evaluate text-based tool-using agents rather than live CUAs, and therefore do not exercise COBRA’s GUI-mediated HTTP enforcement (Zhan et al., 2024; Zhang et al., 2025a). These benchmarks report only whether an attack succeeded against the defense system as a whole, not which component stopped it. STEER-Bench instead groups attacks into suites by the property they violate, such as DFI, and runs each suite with the corresponding defense component enabled and disabled. 

# 3 Threat Model 

Integrity definitions in branching CUAs. We reason about agent execution in terms of control and data flows. An agent satisfies Control-Flow Integrity (CFI) if every action executed at runtime belongs to the pre-authorized plan 3Securing Computer-Use Agents Against Branch Steering Attacks A P REPRINT 

derived from the user’s trusted request. While existing Dual-LLM systems provide CFI by committing to a static sequence of actions ahead of time, dynamic web interfaces force plans to include runtime branches. Branching exposes a separate vulnerability: Data-Flow Integrity (DFI). An agent satisfies DFI if untrusted runtime data cannot influence which authorized branch is executed, nor dictate the security-critical parameters of external actions. Under this framing, standard prompt injections violate CFI (introducing actions the plan never specified), whereas 

branch steering attacks violate DFI: the adversary introduces no new instructions, but crafts untrusted data to steer an authorized branching plan toward an attacker-chosen outcome. 

Attacker capabilities and objectives. We assume the adversary can manipulate untrusted content rendered or returned by third-party web services that the agent navigates during execution, without needing full server compromise. This includes attacker-controlled web elements such as advertisements, user reviews, comments, marketplace listings, incoming messages, and downloaded attachments. On unapproved or compromised external servers, the attacker may additionally control MCP tool descriptions and tool outputs. Following the Kerckhoffs-style threat model, the attacker knows COBRA’s architecture and enforcement mechanisms, but cannot inspect, modify, or adapt to the committed execution plan or the protected state of the interpreter. The adversary pursues two distinct objectives: 1. Control-Flow Integrity (CFI) Violation: Inducing the agent to execute actions entirely absent from the approved plan (e.g., triggering unauthorized tool calls, navigating to malicious domains, or executing arbitrary system commands). 2. Data-Flow Integrity (DFI) Violation (Branch Steering): Supplying adversarial runtime data that satisfies an authorized branch condition or binds action parameters, thereby driving an approved plan down an attacker-favorable path without introducing any new instructions. 

Defender capabilities and scope. COBRA prevents CFI and DFI violations by intercepting and policing side effects at the network and tool boundaries: outgoing HTTP requests and MCP tool invocations. For HTTP traffic, enforcement operates at two granularities depending on metadata availability (Appendix E): • Host-level enforcement (default): Without a sitemap, COBRA restricts network operations to an allowlist of authorized domains derived from the user request and deployment policy, preventing arbitrary navigation or cross-origin data exfiltration. • Endpoint-level enforcement (sitemap-guided): When an approved agent sitemap is available, COBRA’s proxy validates request methods, parametrized URL routes, and payload fields against the specific branch’s constraints. All user approvals of site sitemaps and MCP tool definitions are cryptographically pinned using SHA-256 hashes; any subsequent upstream modification (e.g., tool poisoning or rug-pull attacks) invalidates the hash and halts execution before any untrusted action is dispatched. 

# 4 Architecture 

COBRA consists of a plan interpreter, a central Branch Resolution Hub (BRH), and deterministic HTTP and MCP proxies. The interpreter executes the committed plan, the BRH resolves branch decisions and action parameters using constraints fixed during planning, and the proxies check outgoing HTTP requests and MCP calls against the resolved constraints. Enforcement targets these calls rather than GUI actions because a click does not, by itself, identify the operation it causes. 

Approved descriptions and planning inputs. An agent sitemap describes a site’s operations , such as approving a loan or posting a comment. Each operation specifies an endpoint , an HTTP method and URL template such as POST /loans/{id}/approve , and the named fields carried by the request. MCP tools and their structured arguments provide the corresponding vocabulary for MCP. COBRA uses only site and tool descriptions approved by the user, binding each approval to the artifact’s SHA-256 hash; a changed description requires renewed approval. With an approved sitemap, COBRA can constrain the operations performed on a site. Without one, the planner instead receives a domain allowlist comprising domains designated as trusted in the user’s request and a deployment-maintained list of common infrastructure and analytics domains needed for navigation. Runtime content cannot extend this list. To make sitemaps available for sites that do not publish them, we introduce MESA, which can crawl selected domains on the allowlist and generate candidate sitemaps. This lets us evaluate how sitemap availability affects security and utility (Appendix D). 4Securing Computer-Use Agents Against Branch Steering Attacks A P REPRINT 

Planning and constraint initialization. COBRA generates and annotates a plan before observing untrusted content from the current run. First, the P-LLM generates a program from the trusted request and approved descriptions. If the request requires a security-critical value that neither the user supplied nor a source authorized by the plan can establish, COBRA asks the user for it during plan construction; the supplied value is trusted for that request only. Second, COBRA parses the program to identify its actions and branches. A trusted annotation call assigns each branch its permitted destinations and tools, together with constraints on request fields and tool arguments, using the approved descriptions and the branch’s role in the plan (Appendix A). The interpreter then executes the committed program, calling the Q-VLM where screen observation or interaction is required. The Q-VLM may report observations and propose low-level steps but cannot modify the program. Untrusted content therefore cannot introduce an action absent from the plan, establishing CFI. 

Branch and parameter resolution. The BRH checks branch choices and parameter values reported by the Q-VLM against the constraints active at the current state and the request or call they would produce. An attacker-supplied value can select a branch or fill a parameter only if it satisfies the constraints fixed by the plan. Constraints accumulate through nested branches and are refreshed at each transition, so permissions from an earlier branch do not persist into a later one. 

Enforcement at the HTTP and MCP boundaries. The HTTP and MCP proxies enforce DFI by checking outgoing operations against the BRH’s resolved constraints. A modified ceLLMate proxy (Meng et al., 2026) intercepts HTTP requests, including those triggered by GUI actions. Without an approved agent sitemap, it admits only hosts authorized by the plan. With one, it matches each request to a declared operation and checks its destination and field values (Appendix E). GUI effects that do not traverse HTTP fall outside this boundary. The MCP proxy applies the same resolved constraints to named tools and their arguments. It also verifies that the tool definition matches the approved version, detecting rug pulls, and that the call reaches the approved server, preventing same-name tool shadowing. Appendix F details how COBRA coordinates GUI and MCP interaction under the same enforcement state. 

Fused planning through multi-sample inference. Because the planner cannot observe the environment, a single plan may omit a relevant UI state or failure mode. Fused planning generates five plans in parallel from the same trusted input and merges them, in a final trusted call, into one branching program that retains distinct alternatives. The merged program is committed and processed by the same interpreter, BRH, and proxies as a standard plan. Five candidates provide a favorable empirical trade-off between utility and token consumption (Appendix C). 

# 5 Evaluation 

Setup. Unless stated otherwise, we use gpt-5 as the P-LLM and locally serve UI-TARS-1.5-7B as the Q-VLM. We report attack success rate (ASR), the fraction of attacks that achieve their objective, and task completion without an injection ( benign utility ) or with the injection present ( utility under attack ), as applicable. We evaluate COBRA end to end, including the constraints generated by its planning and annotation pipeline, and determine outcomes from recorded environment state and proxy alerts. The evaluation exercises HTTP enforcement both without approved sitemaps, which restricts the sites the agent may contact, and with them, which also restricts the operations it may perform on those sites. It also exercises MCP enforcement using approved tool manifests. 

Design. STEER-Bench tests COBRA’s components through targeted ablations: each suite runs its attacks against complete COBRA and against a version with the protection targeted by that suite disabled. Each comparison holds the trusted request, intended violation, and models fixed. The benchmark contains 101 tasks, some tested under multiple attack configurations, yielding 199 attack cells and 138 benign cells. A cell is one task run under one configuration. Every attack cell has a corresponding benign reference, but several attack configurations for the same legitimate scenario may share one benign cell, accounting for the difference in counts. Of these, 74 attack cells and 74 corresponding runs without the injection can also be evaluated on generic computer-use agents. The remaining cells exercise capabilities that these baselines lack, including MCP interaction and approval of site or tool descriptions. The tasks span web interactions through the GUI and MCP tool calls, four page-layout families, and domains ranging from bank transfers and warehouse logistics to clinical dosage adjustments. Attack success is scored when the targeted harmful action violates the constraints active at that point, rather than when an attacker completes a broader multi-step objective. 5.1 External Validation 

We evaluate COBRA’s control-flow integrity (CFI), data-flow integrity (DFI), and MCP protections on four published benchmarks beyond STEER-Bench. COBRA blocks every evaluated attack within these protections’ stated scope. The results distinguish protection supplied by plan–execution separation from the additional protection supplied by approved sitemaps and MCP enforcement. 

Plan–execution separation (CFI) and domain-level DFI enforcement. The OS-Harm (Kuntz et al., 2025) prompt-injection cases are already blocked by plan–execution separation: both COBRA and the vanilla dual-LLM system of Foerster et al. (2026) prevent all 51 attacks. To test DFI enforcement without an approved sitemap, we run the 21 cases that attempt unauthorized HTTP requests with a ReAct-style UI-TARS-1.5-7B agent instructed to follow injected on-screen instructions. In this setting, COBRA’s HTTP proxy restricts requests to the domains authorized by the plan. Without the proxy, all 21 unauthorized requests succeed; with it, all 21 are blocked while all corresponding legitimate operations remain permitted. The other 30 cases use channels such as SMTP that the HTTP proxy does not inspect, but remain blocked by the dual-LLM plan–execution boundary. 

Sitemaps and same-site attacks. On WASP (Evtimov et al., 2025), we compare host-level enforcement with enforce-ment using GitLab and Reddit sitemaps from ceLLMate (Meng et al., 2026), treated as approved for the experiment. Without sitemaps, COBRA blocks the five cross-domain attacks, but all 14 attacks invoking an unauthorized operation on the same host succeed; with sitemaps, COBRA blocks all 19 request-level attacks, reducing ASR from 14/19 (73.7%) to 0/19 while preserving 100% benign completion. Tool poisoning and server-side limits. MCPTox (Wang et al., 2026) shows that COBRA blocks tool-poisoning attacks when they change an observable MCP call, but cannot constrain a compromised server’s hidden implementation. Of the 1,223 MCPTox cases, 1,210 change the selected tool or its arguments. COBRA blocks all 1,210 by checking each call against the active branch’s constraints, compared with 100% ASR without enforcement. In the remaining 13 cases, the legitimate and malicious calls use identical tools and arguments, but the server produces a different hidden effect that the proxy cannot distinguish. COBRA achieves 79% utility under attack, compared with 100% without enforcement; the loss primarily reflects failures to generate a suitable and efficient plan rather than legitimate calls blocked by the proxy. 

Tool shadowing and rug pulls. MCPSecBench (Yang et al., 2026) tests whether COBRA prevents a server from impersonating an approved tool and detects changes to a tool definition after approval. Of its 17 attacks, nine fall within COBRA’s threat model. COBRA blocks all nine: five test approved-server binding and hash-pinned tool definitions, while four test whether tool arguments satisfy the active branch’s constraints. It preserves benign utility on all corresponding cases. The remaining attacks target the host’s command namespace, transport, or client and server implementation bugs; tool poisoning is evaluated above using MCPTox.

How far can structural enforcement extend? COBRA checks the committed plan and operations observable through HTTP and MCP, but three questions remain. First, how can it constrain security-critical values that never appear in an HTTP request or MCP call? If a checkout request contains only item identifiers rather than the displayed total, COBRA must read the price from the GUI, where it may not reliably distinguish the site’s price from visually similar attacker-controlled content in an ad or customer review. In this case it cannot enforce a deterministic constraint on the total at the current HTTP or MCP boundaries. Second, how can COBRA check the meaning of free-form content or effects hidden behind an otherwise valid request? Two comments sent to the same endpoint may differ only in whether their text is offensive, while a compromised MCP server may produce a harmful effect despite receiving the same tool call as an honest server. Third, how can COBRA extend enforcement to other computer applications whose actions use protocols or local interfaces outside its HTTP and MCP proxies? An email client may send through SMTP, while a desktop application may write directly to the filesystem; neither action is covered by COBRA’s HTTP and MCP proxies, and many applications do not expose MCP tools. Extending enforcement is difficult because these applications lack a common interface that exposes the semantic meaning of their actions and the values those actions use, which is needed to impose constraints. 

How can blind planning recover from unexpected states without weakening the trust boundary? The lower completion of the same-model COBRA configurations relative to ReAct shows the difficulty of anticipating interface states before execution. Fused planning recovers some later successes on the first attempt, but cannot yet replace repeated independent attempts. A promising direction is to train the P-LLM for computer use rather than encode ever more contingencies in its prompt. Training on task trajectories could teach it recurring routines, such as detecting browser state, dismissing cookie banners, and recovering from failed clicks, while feedback from execution could reward plans that anticipate relevant failure states. Training across website and application layouts could also help it predict likely routes when the request identifies a site or only a category, such as banking or e-commerce. 

Will websites make their operations available to agents in a form that can be secured? The WASP comparison shows that approved sitemaps let COBRA distinguish operations on the same site that host-level restrictions cannot. MCP tool definitions provide a similar vocabulary of named operations and arguments, which can also give agents explicit routes for completing tasks. MESA shows that sitemaps can be approximated by web crawling. Without human revision, its candidate sitemaps contain every operation needed for 18/25 website-facing OSWorld-MCP tasks (72%) and 18/26 Reddit WebArena tasks (69.2%) (Appendix D). Users could maintain such candidate sitemaps themselves, or obtain them from a third party, but either approach requires review and updates as sites change. Site owners are better placed to publish and maintain authoritative sitemaps or MCP tools as part of their services. However, whether they will 8Securing Computer-Use Agents Against Branch Steering Attacks A P REPRINT 

do so remains uncertain, since some may rely on human visits for advertising revenue or may not want to expose their operations to agents. In their absence, COBRA must rely on coarser host-level restrictions or reviewed approximations, while agents have fewer explicit routes for completing tasks. Both stronger security and future utility gains therefore depend in part on whether website owners see value in supporting agents. 

# 7 Conclusion 

COBRA extends Dual-LLM protection beyond control-flow integrity by constraining branch decisions and action parameters, then enforcing the resulting constraints at HTTP and MCP boundaries. STEER-Bench shows that its protections depend on distinct components, and four external benchmarks demonstrate where those protections generalize and where observable requests are insufficient. On OSWorld-MCP, COBRA retains practical task completion, while fused planning brings some later successes into the first attempt. These results show how stronger data-flow guarantees can be added to computer-use agents, while making clear that semantic effects, unsupported channels, and the availability of approved service descriptions remain open challenges.

# Appendix A From a Plan to Enforceable Constraints 

This appendix explains how COBRA turns a committed plan into constraints that the HTTP and MCP proxies can enforce. 

Extracting control flow. COBRA first parses the plan with deterministic code. It records each branch, its alternatives, the plan variable used in its condition, and destinations named directly in the plan. For example, in “if the displayed price is at most $50 ,” COBRA records that the branch depends on the value assigned to the plan’s price variable. This pass fixes the available actions and branches before execution begins. 

Generating constraints. The P-LLM then annotates the fixed plan. Parsing identifies its structure but cannot determine which destinations, operations, request fields, tool arguments, and values the user’s task permits at each point. Using the trusted request, committed plan, and approved site and tool descriptions, the P-LLM specifies these permissions and value constraints for each branch and action. It receives no observations from the current execution. 

Validating observations and selecting branches. Each perception step declares the expected output type, such as a numeric price or a date. The Q-VLM must return a value in the declared format or report that the requested information is not visible, rather than guess. COBRA retries malformed outputs; if validation continues to fail or the Q-VLM reports insufficient information, the step raises an error rather than supplying a guessed value. The interpreter binds the validated value to the plan variable and evaluates the committed branch condition with deterministic code. 

Activating constraints. After evaluating a branch condition, the interpreter passes the selected branch and current validated plan variables to the BRH. The BRH substitutes those values into the branch’s constraints and combines them with constraints inherited from enclosing branches. A missing value, unresolved placeholder, or type mismatch cannot expand permission and causes the applicable check to fail. When execution leaves a branch, the BRH restores the parent state so that permissions from the completed branch do not persist. 

Checking operations. Before an action executes, the BRH checks any Q-VLM-supplied parameter against the constraints active for the selected branch. A disallowed or unresolved value cannot authorize the action. The HTTP and MCP proxies then check the actual outgoing request or tool call against the resolved constraints. For example, if the BRH permits a request carrying $40 in a specified price field, a request carrying $80 in that field is blocked. Both checks use deterministic, typed predicates. If a predicate is unknown or a value has the wrong type, COBRA rejects the action. 

Handling underspecified tasks. During plan construction, the P-LLM identifies security-critical values required by the task and whether the trusted request supplies them or authorizes a source from which to obtain them. If a required value has neither, COBRA asks the user before committing and executing the plan. The answer becomes trusted input for finalizing the plan and its constraints. During execution, the BRH applies only those previously defined constraints; untrusted content cannot trigger further clarification requests.

# C Fused Planning 

Standard COBRA commits to one plan per attempt. Fused planning generates five candidates from the same trusted request and approved descriptions. # D MESA: Generating Candidate Site Descriptions 

Endpoint-level HTTP enforcement requires an approved agent sitemap, but websites rarely publish one, and writing sitemaps by hand is costly and prone to omissions. MESA (MCP and Endpoint Sitemap generator for Agents) reduces this burden: it crawls a site and generates candidate agent sitemaps and MCP tools for the service owner to review and publish. Its output is not trusted by construction. The owner, indeed, may edit or reject any entry before publication, and a COBRA user then separately decides whether to approve a published artifact as trusted planning input. This appendix describes MESA’s pipeline and evaluates the coverage of the artifacts it produces. 

1. Collecting evidence. MESA visits the target site with a browser, follows links, and records pages, forms, fields, and navigation paths up to a configurable page limit. Site content is treated as untrusted evidence: model prompts delimit it as data rather than instructions. For sites that require login, MESA can crawl using a previously authenticated browser session, allowing it to observe pages and operations available to that user. 

2. Proposing capabilities. From the crawl evidence, a model proposes a list of operations, ordered by expected importance, that capture common agent tasks such as searching, viewing, creating, or editing resources. It excludes incidental assets, tracking requests, and CDN traffic. 

3. Service-owner review. The website or MCP service owner reviews the candidates and may edit, remove, or add entries before publication. MESA reduces drafting effort but does not certify its output. Even after the owner publishes them, COBRA uses them for planning only if the user approves them. 

4. Materializing sitemaps and tools. For each curated operation, MESA generates the HTTP method, a URL template with placeholders and query parameters, an action label, and any request-body fields. It then derives one MCP tool from the same operation, using the URL placeholders and body fields as tool arguments. These details define the vocabulary available to COBRA’s annotation process: a field omitted from the sitemap cannot later receive a field-level constraint. 

5. Validating output. A deterministic final pass preserves the crawled origin, removes exact duplicates, and checks structural consistency between HTTP and MCP representations. It may flag operations that resemble sensitive actions for closer owner review. Published artifacts remain subject to separate approval by each COBRA user. 

Evaluation (description coverage). MESA addresses the deployment precondition for endpoint-level HTTP enforce-ment by generating candidate agent sitemaps and corresponding MCP tools from existing websites. Because no gold standard exists for these artifacts, we evaluate their functional coverage against the operations required by tasks from WebArena and OSWorld-MCP. For 26 Reddit tasks from WebArena, we record the functions and parameters used by an agent to solve each task and check whether they are represented in the generated artifacts. # E Sitemap-Conditioned HTTP Guarantees 

Enforcement tiers. COBRA provides CFI independently of sitemap availability: the interpreter activates only actions and transitions contained in the committed program. Sitemaps instead determine the granularity of HTTP enforcement. Without an approved agent sitemap, COBRA derives an allowlist from the hosts specified by the trusted plan and blocks requests to other hosts. This host-level enforcement applies to any website, but cannot generally distinguish different operations performed through endpoints on the same authorized host. An approved sitemap provides a closed HTTP action space whose entries specify an HTTP method, URL template, named body fields, and semantic description. The P-LLM selects the operations required by the plan, and the HTTP proxy rejects requests whose method or endpoint is not selected. This enables endpoint-level enforcement analogous to restricting MCP calls to approved tools. The evaluation on WASP illustrates this distinction. Without a sitemap, host-level enforcement blocks the five cross-domain attacks but leaves same-host operations indistinguishable. With an approved sitemap, endpoint constraints block 14 additional attacks, bringing the total to 19 of 21. The remaining two produce the authorized request but differ in a semantic property of free-form text, which cannot be expressed as a deterministic request-level constraint. 

Retrieval and approval. For each domain referenced by a plan, COBRA attempts to retrieve 

https://domain/sitemap.json via HTTPS. Retrieval produces only a candidate artifact: the sitemap is neither exposed to the P-LLM nor used for endpoint-level enforcement until the COBRA user explicitly approves it. A missing, invalid, or unapproved sitemap leaves the site under host-level enforcement. The user reviews the complete sitemap, including its free-text descriptions. After approval, COBRA canonically serializes the artifact, computes its SHA-256 hash, and stores the hash in a per-domain registry. A retrieved sitemap is admitted as trusted planning input only when its hash matches the approved version. If any part of the sitemap changes, including a semantic description, the new version is withheld, the user is notified, and renewed approval is required. Until approval, the modified sitemap contributes nothing to the planner’s action space and the site remains under host-level enforcement. 

Relation to MCP. Sitemap-conditioned HTTP enforcement and MCP enforcement follow the same construction: a trusted, machine-readable action space is fixed before execution, the plan selects permitted operations, and deterministic proxies reject operations outside that selection. For MCP, tool definitions and input schemas provide this action space by protocol convention. Websites rarely publish equivalent agent sitemaps, so endpoint-level HTTP enforcement applies only when a sitemap has been published or generated, reviewed by the COBRA user, and bound to its approved version. All other sites retain host-level enforcement. To reduce the burden on site owners, MESA generates candidate agent sitemaps for them to review, approve, and publish (Appendix D).

In the planning role they tend to generate short programs that often fail to parse or execute, limiting task completion. This result motivates pairing a stronger, infrequently invoked P-LLM with a locally served Q-VLM; the pilot is too small to establish a general ranking of planner models. 

# H OpenCUA Utility Results 

We separately evaluate OpenCUA-7B and OpenCUA-32B on the same 361 OSWorld-MCP tasks used in Section 5.2. For each model, we compare a ReAct agent with a COBRA configuration that uses gpt-5 as the P-LLM and the corresponding OpenCUA model as the Q-VLM. All configurations use pass@5 with early stopping and a 20-step limit per attempt. Completion requires an exact OSWorld score of 1.0.Table 7 shows that the effect of adding a separate planner depends on the interaction model. With OpenCUA-7B ,COBRA raises completion by 8.6 percentage points and matches or improves the ReAct result in every domain. With 

OpenCUA-32B , the aggregate gain is 2.5 points and the domain-level results are mixed: COBRA improves Writer, Impress, Multi-apps, VLC, and VS Code, but loses completion on Chrome, Calc, and Thunderbird. This pattern suggests that a strong external planner is most useful when it complements a smaller interaction model; as the Q-VLM becomes more capable, blind planning can add less utility and may constrain strategies that the reactive agent would otherwise discover. 16
