## 摘要
间接提示注入（IPI）将指令植入使用工具的LLM智能体所读取的内容中，诱使智能体进行有害的工具调用。最强的防御位于系统层面，利用任务条件工具筛选等技术来阻止恶意工具执行，以及信息流控制来避免使用不可信参数执行工具。然而，随着智能体能力增强，用户将更多事务委托给自动化。因此，工具执行序列和参数值越来越多地在运行时确定，仅凭用户查询无法可靠筛选，否则会显著损失效用。我们提出ROPE（路由来源策略执行），其基于一种结构化的信任概念：一个值只有在能够不可伪造地追溯到用户、用户明确指定的来源或用户自身的权威记录时，才能到达改变状态的工具。该执行机制是对一组受审计的敏感工具参数进行确定性的来源检查，并且对语言模型的唯一依赖仅涉及可信的用户请求，超出攻击者的影响范围。我们的方法具备两项可证明的保证：1）在轨迹的每一步，任何仅源自攻击者可写内容的值都不会到达受来源保护的参数；2）对注入内容的任何改写都不会改变准入决策。我们在四个智能体模型和开放式智能体测试套件上进行了评估，ROPE将攻击成功率控制在1.6%至2.6%，同时保留了未防御时82%至100%的干净效用，在效用上显著超过现有最先进的系统级防御，同时达到相当或更好的安全性。此外，我们表明针对ROPE优化注入内容在很大程度上无效，而击败先前系统级防御的长时程攻击成功率为零。我们的代码和日志可在 https://github.com/xhOwenMa/ROPE 获取。

## Abstract
Indirect prompt injection (IPI) plants instructions in the content a tool-using LLM agent reads, steering the agent into harmful tool calls. The strongest defenses are system-level, leveraging techniques such as task-conditional tool screening to prevent execution of malicious tools, and information-flow control to avoid tool execution with untrusted parameters. However, as agents grow more capable, users delegate more to automation. Consequently, tool execution sequences and parameter values are increasingly determined at runtime and cannot be reliably screened from solely user's query without significant utility loss. We present ROPE (Routed Origin Policy Enforcement), which is anchored in a structural notion of trust: a value may reach a state-changing tool only if it traces unforgeably to the user, a source the user explicitly named, or the user's own authoritative records. Enforcement is then a deterministic origin check over an audited set of sensitive tool parameters, and the only reliance on a language model involves solely the trusted user request, out of the attacker's reach. Our approach admits two provable guarantees: 1) at every step of a trajectory, no value whose only origin is attacker-writable content reaches an origin-guarded parameter, and 2) no rewording of an injection changes an admission decision. We evaluate across four agent models on open-ended agent suites, ROPE holds attack success rate to 1.6--2.6\% while retaining 82--100\% of undefended clean utility, significantly exceeding state-of-the-art system-level defenses in utility while attaining comparable or better security. Further, we show that optimizing the injection against ROPE is largely ineffective, while long-horizon attacks that defeat prior system-level defenses achieve zero success rate. Our code and logs are available at https://github.com/xhOwenMa/ROPE .

- **现有防御局限**：
  - 系统级防御主要分为两类：基于任务条件工具筛选（如 DRIFT、Progent）和基于信息流控制（如 CaMeL、PFI）。
  - 这些防御要么因过度保守而大幅牺牲任务完成率（效用崩溃），要么因在运行时引入 LLM 判断而扩大了攻击面，难以在开放、动态、需要运行时重规划的任务中同时保持安全与效用。

- **ROPE 目标**：通过利用系统中已有的结构信任锚，在不牺牲动态性和效用的前提下，对状态更改工具的参数进行确定性来源检查，从根本上阻断攻击者控制的值进入敏感参数。

## 2. 论文提出的方法论：核心思想、关键技术细节、算法流程

- **核心思想**：一个值只有在能够不可伪造地追溯到用户本身、用户明确指定的来源、或用户自己的权威记录时，才允许到达状态更改工具。信任是基于值的**来源**而非其文本内容。
- **三个信任锚**（T1/T2/T3）：
  - T1：用户的真实请求（query）本身。
  - T2：用户请求中明确引用的、带有不可伪造运行时身份的值（如经签名/认证的邮件发送者地址）。
  - T3：用户自己的权威记录（如平台维护的用户订单历史、账号自有的 SSH 密钥状态），这类字段只能由用户认证过的动作写入，且写入内容本身必须经过来源检查。
- **系统架构与流程**：
  1. **一次性离线设置**：从工具模式中识别所有非只读的状态更改工具，并标记其敏感参数（如收款人、收件人、目标路径、内容体）。该表是静态、可审计的。
  2. **Step 1 路由与范围界定**：由一个 LLM 只读取用户请求（不读取任何运行时的外部内容），输出任务的**欠规格化级别**（完全指定、参数开放、动作开放）和**作用域**（用户点名的不可伪造来源、用户明确写出的参数值）。由于输入是可信的，注入内容无法影响该步骤。
  3. **Step 2 编译确定性策略**：根据欠规格化级别，为每个敏感参数分配一个来源标记（marker）。标记包括 `PROMPT`（仅请求）、`SOURCED`（请求或命名来源）、`RECORD`（请求或用户权威记录）、`FREE`（自由文本体）、`DEST`（写入目标路径限制）、`EXPLICIT`（不可逆操作需显式授权）等。
  4. **Step 3 运行时强制执行**：一个**来源跟踪器**根据工具调用和结果的结构（例如邮件签名、账户记录 vs. 文件正文）标记每个读取值的来源。当智能体尝试状态更改调用时，**匹配器**检查每个敏感参数的值是否匹配来源策略允许的值。只读工具调用始终通过，不惩罚良性偏差。
- **关键设计点**：
  - 强制执行是确定性的，无 LLM 在回路中，因此不存在可被注入内容攻击的 LLM 判断面。
  - **决策单元匹配**：整个标识符（如 owner/repo、邮箱地址、URL 主机）作为不可分割的匹配单元，防止攻击者用 `attacker/victim-repo` 包裹可信名称绕过检查；列表参数要求所有元素都可信。
  - **审计默认钳制**：每个敏感参数都有离线默认标记，路由器的每任务覆盖不能放宽到默认之下，从而限制弱路由器带来的安全风险。
- **可证明保证**：
  - **来源健全性**（Proposition 1）：在 A1 来源完整性、A2 记录完整性、A3 枚举完整性成立下，任何仅源自攻击者可写内容的值都不会到达来源保护参数。
  - **改写不变性**（Proposition 2）：注入的措辞改写不会改变准入决策，因为决策只依赖值、来源和编译后的策略，路由器仅读取可信请求。
  - **记录闭包**（Lemma 1）：确保被准入的状态更改调用不会污染 T3 权威记录。

## 6. 论文的主要结论与发现

- ROPE 在四个智能体模型上，将 AgentDyn 的攻击成功率控制在 **1.6–2.6%**，同时保留未防御时 **82–100%** 的干净任务完成率，显著优于现有系统级防御。
- 在 AgentDyn 上，ROPE 是唯一同时实现高实用性和低攻击率的防御；其他防御要么保留效用但攻击率高，要么降低攻击率但效用崩溃。
- 自适应攻击（AutoDojo）对 ROPE 几乎无效，优化后的 ASR 变化不超过几分之一百分点；而基于运行时判断的 DRIFT 等防御在优化攻击下 ASR 显著上升。
- 长时程攻击（AgentLAB）对 ROPE 的成功率为 **0%**，且保持接近未防御智能体的任务完成率。
- 策略消融显示：固定严格策略降低效用，固定宽松策略大幅提高攻击率，而 ROPE 的路由策略可在两者之间取得最佳平衡。
- 更便宜的路由器结合审计默认钳制后，安全性接近参考路由器，仅损失有限效用，证明防御架构可以限制弱路由器的安全风险。
- 失败分析表明残余攻击成功主要来自三类：模型输出消息本身的有害内容、合法的自由文本消息体、以及委托给攻击者可写内容的参数，均不在来源保护保证范围内。

## 7. 优点

- **安全与效用兼顾**：在动态、开放任务上首次实现低攻击率与高任务完成率并存，解决了现有防御的效用崩溃问题。
- **确定性执行、无 LLM 攻击面**：强制执行仅依赖值来源而非内容，不引入可被注入内容攻击的 LLM 判断环节。
- **可证明保证**：提供来源健全性和改写不变性两项理论保证，为安全提供形式化基础。
- **利用平台结构信任锚**：将现有安全机制（签名邮件、账户记录）纳入信任模型，扩大可保护范围。
- **路由器的审计默认钳制**：即使路由器较弱或出错，也能通过离线默认策略限制其放宽范围，降低部署风险。
- **匹配器设计严谨**：决策单元全值匹配、列表全元素可信等规则防止常见绕过。
- **实验评估全面**：覆盖多模型、多基准、多攻击类型、多基线对比及消融，并对评分进行了公平性校正。
- **失败分析透明**：详细分类残余攻击成功和干净任务失败，明确自身局限，便于理解适用范围。

## 8. 不足与局限

- **平台依赖强**：需要系统提供不可伪造的来源元数据、记录完整性保证、敏感工具枚举等，现实平台中这些支持可能不完整或不一致。
- **只保护工具调用，不保护模型输出**：对于不涉及工具调用的有害消息（如智能体回复中的钓鱼链接）无能为力。
- **无法处理“值仅存在于攻击者可写内容”的委托场景**：当合法值本身源自可注入内容时，ROPE 会拒绝该值，导致任务失败（fail-closed），虽然安全但损失效用。
- **需要离线精确枚举敏感工具和参数**：枚举遗漏会直接破坏保证；且存在像 `browse_webpage` 这类接口表现为只读但实际可能触发状态更改的工具，枚举困难。
- **假设较强**：威胁模型假设攻击者不能伪造来源身份、不能写用户权威记录、工具和工具描述可信，实际部署中这些假设可能不完全成立。
- **实验环境有限**：主要基于模拟基准，未在真实生产系统（如真实银行、邮件平台）中验证，迁移到现实场景的实用性尚待检验。
- **某些基线可能未最优适配**：例如 CaMeL 在开放任务上完成率为 0，PFI 的标签与策略由作者重新提供，可能影响对比的公平性。
- **记录闭包的一个边缘条件**：订单日志在持续环境中的写入可能污染未来的 RECORD 来源，论文虽提出解决方案但未在评估中实现。
