## 摘要
语言模型智能体通过所赋予的工具行动。它在执行任务时读取的数据可能改变它使用这些工具的行为。因此，越来越多的用于安全可靠智能体执行的技术位于智能体与其工具之间，旨在在该边界上实施访问控制、信息流或隔离。如今，这些技术在围绕间接提示注入构建的智能体安全基准上进行评估。这些基准通过衡量防御在保持智能体效用的同时将成功攻击数量降低多少来评判防御。防御仅根据智能体的执行情况进行评判。它可能在两个指标上得分很高，同时保持着任何任务都不需要的转账、删除或广泛读取的开放权限。Ajar 利用现有基准直接测量这种开放权限。它附加到一个已存在的智能体安全基准上，并重用该基准用于对其自身运行进行评分的任务、工具模式、参考解和目标状态。对于每个良性任务，它构建该任务不需要的候选工具调用，因此允许其中一个就是留下了开放权限。这些调用在智能体可能行动的每个点呈现给防御。我们通过将 Ajar 附加到 AgentDojo 上来评估它，其中开放权限成为继现有攻击成功率和良性效用之后的第三个轴。我们在五种防御上运行它：Progent、CaMeL、AC4A、Permission Assistant 和 Claude Code 的 Auto 模式。我们观察到它们留下的开放权限数量差异很大。两种防御泄漏的数量几乎相同，但在完成的良性任务上差异很大，而一种防御通过拒绝其任务有权进行的调用来换取部分严格性。这种开放权限无法从测量的攻击成功率或良性效用中推导出来。Ajar 的源代码可在 https://github.com/reSHARMA/Ajar 获取。

## Abstract
A language model agent acts through the tools it is given. The data it reads while working on a task can redirect what it does with those tools. A growing set of techniques for safe and secure agent execution therefore sits between the agent and its tools, aiming to enforce access control, information flow or isolation at that boundary. Today these techniques are evaluated on agent-security benchmarks built around indirect prompt injection. Those benchmarks judge a defense by how far it brings the number of successful attacks down while preserving the agent's utility. A defense is judged only on the agent's execution. It can score well on both metrics while holding open a transfer, a deletion or a broad read that no task needed. Ajar measures that open privilege directly using the existing benchmarks. It attaches to an agent-security benchmark that already exists and reuses the tasks, tool schemas, reference solutions and goal states that benchmark uses to grade its own runs. For each benign task it builds candidate tool calls the task does not need, so allowing one is privilege left open. These calls are presented to the defense at every point where the agent could act. We evaluate Ajar by attaching it to AgentDojo, where open privilege becomes a third axis beside the existing attack success and benign utility. We run it on five defenses: Progent, CaMeL, AC4A, Permission Assistant, and Claude Code's Auto mode. We observed that they leave widely different amounts of privilege open. Two defenses leak by almost the same amount yet differ widely in the benign tasks they finish, and one defense buys part of its tightness by refusing calls its tasks were entitled to make. This open privilege cannot be derived from the measured attack success or benign utility. The source code of Ajar is available at https://github.com/reSHARMA/Ajar.

## 1. 论文的核心问题与整体含义

- **研究背景**：语言模型智能体通过工具行动，间接提示注入可使执行任务时读取的不可信数据改变其工具调用行为。为此，大量防御技术部署在智能体与工具之间，在工具调用边界做访问控制、信息流控制或隔离。
- **核心问题**：现有智能体安全基准主要报告两个指标——攻击成功率（attack success rate）与良性任务效用（benign utility）。二者都只基于“实际发生的那一次运行”计算，无法反映防御“本来会允许”但智能体从未提出的权限。
- **问题表现**：一个防御可能在攻击成功率和良性效用上都表现很好，却仍保留着任务完全不需要的转账、删除或广泛读取权限；这种“开放权限”（open privilege）等待更强大模型或新注入攻击去利用。
- **整体含义**：最小权限原则无法由攻击成功率和效用分数度量。论文提出 Ajar，直接在现有基准上测量防御留下的开放权限，使其成为继攻击成功率、良性效用之后的第三评估轴。

## 2. 论文提出的方法论

- **基本框架**：Ajar 附着到已有智能体安全基准，重用该基准自带的良性任务、工具模式、参考解和目标状态。它不运行智能体，而是用生成测试直接询问防御“是否会允许某个调用”。
- **决策点与测试**：
  - 决策点是任务参考解执行前缀的某个状态，即执行 0、1、2……个任务自身调用后的状态。
  - 一个测试 = 在某个决策点向防御呈现一个候选工具调用 + 该调用的真实标签（allow/deny）。
- **统一防御接口**：所有防御通过 `decide(call, context) → {allow, deny}` 接口被包装。上下文包含已执行前缀及防御自身状态；必要时 Ajar 会重放参考解前缀，让有状态防御看到与真实运行一致的历史。
- **候选调用生成**：
  - 必需调用（required calls）：参考解中的每一步，用于测量防御是否误拒绝任务必需的操作。
  - 许可但非必需调用（permitted calls）：包括任务有权读取的数据、参考解在等价可行顺序下的调用，用于测量过度限制。
  - 过度调用（excess calls）：任务不需要的调用，分为三类：
    1. 路径外工具：调用任务从不使用的工具。
    2. 参数错误：对已授权调用更换参数，如错误资源、参数扩大、类型违规、参数缺失。
    3. 攻击者埋设调用：来自基准自带的注入攻击所指向的 sink 调用。
- **伤害分层**：
  - H0：必需调用，权重 0。
  - H1：可逆、自范围读取或草稿，权重 1。
  - H2：可逆、影响第三方的操作，权重 3。
  - H3：不可逆、自范围操作，权重 9。
  - H4：不可逆、影响第三方或资金，权重 27。
- **核心公式**：
  - 过度权限泄漏：  
    \( OPL(D,t) = \frac{\sum_{c \in C^-_t} w(c)\mathbf{1}[d(c)=allow]}{\sum_{c \in C^-_t} w(c)} \)  
    即防御允许的过度调用中，经伤害加权后的比例。
  - 供给不足：  
    \( UP(D,t) = \frac{|\{c \in C^{req}_t : d(c)=deny\}|}{|C^{req}_t|} \)  
    报告“充分性”为 \(1-UP\)。
  - 过度限制：另行统计防御拒绝“任务有权但非必需”调用的比例。
- **Oracle 标签来源**：
  - 部分标签由 AgentDojo 自身谓词验证，例如攻击 sink 调用触发 security() 谓词为真，或参考解写入后 utility() 仍为真。
  - 其余标签由 Ajar 根据任务必需工具集和目标状态断言；论文清楚记录已验证与断言标签的比例。

## 3. 实验设计

- **宿主基准**：AgentDojo v1.2.2，包含 banking、slack、travel、workspace 四个套件，共 97 个良性用户任务。

  - 生成 10,471 个测试，来自 3,551 个唯一候选调用。
  - 决策点深度从 0 到 18。
  - 其中 9,039 个为 deny 标签测试，339 个 required，1,093 个 permitted。
  - 标签中 2,822 个（27.0%）由 AgentDojo 谓词验证，其余 7,649 个由 Ajar 断言。
- **被测防御**：
  - Progent：基于策略的权限控制，随工具结果动态更新允许列表。
  - Permission Assistant：逐调用权限预测分类器。
  - CaMeL：信息流控制系统，检查可信规划器输出程序的 capability。
  - AC4A：面向工具型与浏览器型智能体的访问控制系统，策略由模型每任务实例写入一次。
  - Claude Code Auto mode：已部署编码智能体的自动模式，逐调用决策。
- **决策模型**：
  - Progent、CaMeL、AC4A、Permission Assistant 在两个模型下运行：Sonnet-5 和 Haiku-4.5。
  - Claude Code Auto mode 仅支持 Sonnet-5。
  - 模型由 Amazon Bedrock 提供。
- **对比基线**：
  - allow-all：允许所有调用。
  - deny-all：拒绝所有调用。
  - tool-name allowlist：只按工具名允许，不约束参数。
  - argument-exact oracle：基于真实参数的精确允许列表。
- **附加实验**：
  - 良性任务完成成本：每个防御在 97 个良性任务上分别运行有防御与无防御两次。
  - Progent 更新步骤消融：动态策略 vs 冻结初始策略。
  - 伤害权重敏感性、测试预算子采样、任务措辞改写、重复运行方差等。

## 6. 论文的主要结论与发现

- **开放权限是独立第三轴**：OPL 分离了攻击成功率和良性效用无法区分的防御。
- **泄漏与效用的非单调关系**：
  - 两个防御的泄漏差异小于 0.009，但良性任务完成率相差 37 个百分点。
  - 更紧的防御反而完成更多任务，因此 OPL 不能从效用预测。
- **防御之间泄漏差异明显**：
  - 例如 Permission Assistant（Sonnet-5）OPL 为 0.0810，Claude Code Auto mode 为 0.3009。
  - tool-name allowlist 基线为 0.3551，argument-exact oracle 为 0.0020。
  - 所有防御都远高于可同时“紧密且可用”的 oracle 区域。
- **严格性可能来自拒绝合法调用**：
  - CaMeL 在 Sonnet-5 下是第二紧的防御，但拒绝了最多的合法调用，过度限制率约为 Permission Assistant 的近五倍。
  - OPL 与过度限制并不绑定。
- **分数属于整个决策过程，而非防御本身**：
  - 改变决策模型会改变 OPL，且方向不一。
  - 较小模型通常同时降低充分性和完全供给任务数，不是沿效用-权限前沿滑动。
  - 同一输入重复运行也会产生方差。
- **测量稳定性**：
  - 伤害权重改变时，排序基本保持，Kendall’s τ 不低于 0.673。
  - 测试预算超过约 25% 后 OPL 趋于稳定。
  - 任务措辞改写不会一致地改变 OPL，排序大体保持。
- **攻击成功率在当前基准上的局限**：AgentDojo 的某类指令攻击对无防御智能体已不成功，因此论文不报告自己的攻击成功率，而用 attack admission 联系开放权限与注入 sink。

## 7. 优点

- **弥补关键盲点**：直接测量未执行路径上的开放权限，而不是只统计已经发生的成功攻击或任务完成情况。
- **工程解耦清晰**：Ajar 通过 host benchmark adapter 和 defense wrapper 与外部系统交互，只需各写一个适配层即可迁移。
- **形式化分数设计**：
  - OPL 与 sufficiency 配合使用，避免“全拒绝”或“全允许”的退化最优。
  - 伤害权重区分低风险和高风险过度调用，使分数更贴近实际危害。
- **透明性较好**：明确记录哪些标签由基准谓词验证、哪些由 Ajar 断言，并讨论 construct validity 边界。
- **实验敏感性分析充分**：伤害权重、测试预算、任务措辞、重复方差、置信区间等多维度验证结论稳定性。
- **代理无关设计**：Ajar 不运行智能体，避免智能体模型干扰防御分数，使分数更直接归于防御决策过程。
- **贴近真实部署**：包含对已部署系统 Claude Code Auto mode 的评测，且支持有状态防御（如 Progent）的逐决策点测量。

## 8. 不足与局限

- **Oracle 标签依赖自身判断**：
  - 73.0% 的标签由 Ajar 断言，只有 27.0% 由 AgentDojo 谓词验证。
  - 边界候选调用可能被不同人标注为不同结果，论文明确承认 construct validity 局限。
- **测试覆盖不完整**：
  - 候选参数来自环境、参考解或注入，无法覆盖环境中不存在的

- 候选参数来自环境、参考解或注入，无法覆盖环境中不存在的对抗性参数或未来攻击者可能构造的变体，因此 OPL 可能低估开放权限的实际可利用面。
- **防御 wrapper 集成偏差**：不同防御需要定制 wrapper，以提供其所需的上下文（如策略、工具结果、规划程序等）；wrapper 的信息呈现方式可能与真实运行不完全一致，从而引入测量偏差。
- **主结果仅单次运行**：虽然对部分防御做了 3 次重复运行并报告方差，但主结果每个配置仅运行一次，模型随机性可能影响相邻防御的排序稳定性，尤其是 OPL 差异很小的防御对。
- **成本与效率未报告**：防御在决策时的延迟、token 消耗、经济成本及对端到端任务效率的影响均未测量，无法评估实际部署的可行性。
- **任务与领域范围有限**：仅在 AgentDojo 的 banking、slack、travel、workspace 四个领域上评测，任务规模和工具模式相对固定，是否推广到其他工具环境或真实系统仍需验证。
- **防御类型适配局限**：Ajar 依赖统一的 `decide(call, context)` 接口，对于不暴露逐调用决策、或依赖用户交互、异步反馈的防御系统难以直接适配。
- **开放权限与实际攻击成功之间的差距**：论文使用 attack admission 将开放权限与注入 sink 联系起来，但没有证明所有 OPL 中捕获的开放权限都能被现有攻击直接、稳定地利用；高 OPL 表示权限暴露，但不等于当前攻击即可成功。
- **标签主观性未完全消除**：虽然透明地记录了验证与断言比例，但 permitted calls 和部分 boundary calls 的标签仍可能受标注者判断影响，不同任务或套件间的一致性尚未量化。
