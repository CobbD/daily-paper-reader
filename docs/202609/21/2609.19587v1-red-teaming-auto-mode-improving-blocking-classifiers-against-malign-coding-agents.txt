## ABSTRACT 

To keep coding agents from going off the rails, production systems now review each proposed action with a blocking monitor that can reject it before it runs ( Auto Mode in Claude Code, Guardian in OpenAI’s Codex). Prior evaluations of such monitors largely measure robustness to accidental harm or prompt injections from untrusted sources looking to hijack the agent. Less understood is how they hold up when the agent they monitor is persistently misaligned. To understand this risk, we task an adversarial agent with evading production blocking monitors and causing catastrophic harm, e.g. by exfiltrating its own weights. We find that when instructed with high-level attack strategies, adversarial agents can succeed through several distinct mechanisms, such as agent-generated prompt injection against the monitor, multi-agent attacks, and malicious compaction. In particular we find that in 79% of trials, the agent can use an injection attack against Auto Mode 

and Guardian to run arbitrary bash commands. We also find that it is possible to greatly improve Auto Mode through design changes like enhancements to tool coverage, transcript formatting and an agentic monitor stage. Even with these improvements, preventing multi-context attacks at an acceptable cost remains an open problem. By detailing our red-teaming methodology and highlighting new attack vectors, we aim to help defenders evaluate their mitigations against the possibility of persistent malign coding agents. Code is available at https:// github.com/safety-research/red-teaming-auto-mode .

## 1 INTRODUCTION 

Coding agents can now run for days with little or no human involvement, completing software tasks end to end (Kwa et al., 2026). That autonomy requires broad access to the environment: a shell, the filesystem, credentials, and the network. This poses the risk of an agent taking reckless or dangerous actions with its access to the user’s system. Most dangerous actions by agents to date have been the result of over-eagerness while completing a task. However, persistent adversarial agents attempting to attack the infrastructure hosting them are an emerging threat, as demonstrated by the recent Hugging Face incident and related events (OpenAI, 2026; Anthropic, 2026; UK AI Security Institute, 2026). These examples raise a new question: How do we deploy coding agents for long-horizon tasks given the increasing risk of severe, hard-to-reverse harm? Blocking monitors (Lindner et al., 2025; Stickland et al., 2025) have been developed and tested for the over-eagerness failure mode—they check each action (e.g. a bash command) against a separate LLM-based classifier, and block unsafe actions, after which the agent proposes a new action. This resembles the resample protocols of Bhatt et al. (2025), but there the step is resampled from the same context, whereas in this work the agent sees why it was blocked. Claude’s Auto Mode (Hughes, 2026) and Codex’s Guardian (Tr˛ ebacz et al., 2026) are the most widely used versions of these in production currently. The common features of these two monitors are (a) they evaluate actions against a set of rules, (b) they can block with a reason that is fed back to the agent, and (c) they terminate a session after exceeding some number of blocks.

In this work we study production blocking monitors under the new threat of persistent adversarial agents. Unlike asynchronous monitors, blocking monitors are on the critical path for preventing immediate catastrophic harms. These include exfiltration of data—their own model weights in the most extreme case—and evasion of the blocking monitor by disabling it or creating new unmonitored agents. These exfiltration and rogue deployment scenarios are two of the most important threats in AI control, and motivate the improvement of the monitors in question via adversarial red-teaming. Production monitoring systems change constantly, so our results are a snapshot of their robustness as of September 2026. The attacks, tools, and design principles we report are intended to outlast this snapshot. 

## 2 RELATED WORK 

AI Control. We adopt the AI Control framework (Greenblatt et al., 2023), in which the moni-tored model deliberately subverts its safeguards, and evaluate the monitors in AI Control settings (Kaufman et al., 2025; Tracy et al., 2026; Kutasov et al., 2025). We build on the trusted monitor-ing protocol, where the monitor is assumed not to collude with the agent (see Section 5). Whilst MonitoringBench (Jotautait˙ e et al., 2026) and SLEIGHT-Bench (Najt et al., 2026) score monitors on fixed attack trajectories, we run adaptive attackers live against production monitors. 

Prompt injection. Indirect prompt injection (Greshake et al., 2023) plants instructions in the agent’s inputs. Terekhov et al. (2026) showed that the untrusted model can instead inject the monitor, embedding known injection strings in its outputs on control benchmarks. (2024) show that per-response classifiers cannot contain information that leaks across such a sequence of smaller requests. Makins et al. (2026) and Hills et al. (2026) apply decomposition to agents. Our red-team evaluations fall into three modes, ordered roughly by increasing cost and fidelity. 

Analytical evaluation looks for discrete vulnerabilities. Reading the monitor’s prompts, code, and integration with the surrounding system directly yields attack hypotheses, such as unmonitored tool calls, injection channels, unhandled prompt edge-cases, and points where agent output is promoted to user intent. 

Replay-based evaluation scores existing transcripts against a monitor. In a loose analogy with reinforcement learning, replay is off-policy : it is agnostic to the policy that produced a transcript. This makes replay cheap and lets us reuse transcripts from prior work or optimize certain parts of the transcript freely, but it does not capture the attacker vs. defender interaction. • Benign replay: we use a cross-section of 4,000 actions from the SWE-chat dataset (Bau-mann et al., 2026) to measure deployment metrics such as false-positive rate (Figure 8). • Malign replay: attack transcripts, used to score and optimize attacks against a monitor without running an agent (e.g. Figure 5b). 

Rollout-based evaluation runs a red-team agent (primarily Opus 5) live against the monitor. We use the agent’s system prompt to steer it toward an attack category and to grant affordances such as knowledge of the monitor formatting (Appendix B). Rollout is the on-policy counterpart to replay: the trajectory is generated by the attacker policy under test as it interacts with the monitor, so rollout success rates are our most credible estimates of real risk. • Arena: a real Claude Code agent, acts in Docker-based environments (LinuxArena (Tracy et al., 2026), BashArena (Kaufman et al., 2025), and custom tasks) with side tasks scored by deterministic checkers, a replaced system prompt and hooks that route each action through the monitor before it runs. Compared to simulation below, arenas enable long evaluation trajectories with deterministic environment outputs. • Simulation: An evaluation featuring bash , write , and edit tools, where tool outputs are generated by an LLM dungeon master (DM). The DM is prompted with a scene descrip-tion and determines when the side-task is complete. This approach allows the simulation of complex weight exfiltration and rogue deployment environments without building infras-tructure. 4Preprint 3.4 AUTOMATED RED -TEAMING 

We automate parts of red-teaming to generate and evaluate attacks: 1. For monitor injection attacks, we use an OPRO-style (Yang et al., 2024) optimization loop (Appendix A.1.4): a proposer model iterates on an injection string, hill-climbing on the fraction of a fixed set of base transcripts on which the injection bypasses the monitor. 2. For compaction attacks and policy failures in the simulation environment, we use an in-vestigative fuzzing agent which creates many transcripts to identify vulnerabilities. Given a brief describing a main task, side task, and scene, the agent can craft attack transcripts and invoke the monitor. A judge decides if the attack transcripts are plausible enough to demonstrate vulnerability in the monitor. See Appendix F for more.

We present our findings as a game between a red-team that constructs attacks and a blue-team that hardens the monitor against them, played iteratively: each attack we find motivates a moni-tor change, which invites the next attack. 4.1 AGENTS ARE ABLE TO EXPLOIT HOLES IN THE SYSTEM TO BYPASS AUTO MODE 

Monitoring systems have discrete vulnerabilities: an action that is never reviewed, or a gap in the policy’s wording. We identified and fixed several such vulnerabilities in Claude Code as part of this work. The most serious vulnerabilities were unmonitored channels : Compaction summaries were not monitored, so an agent could fabricate facts about the environment or the user’s intent and have them treated as trusted context after the compaction. The multi-agent workflow tool was similar: workflow creation and agent-to-agent handoffs let an agent inject instructions into messages that a subsequent agent reads as user authorisation. We also found discrete policy holes . For example, the policy reliably blocks launching a Claude instance with permissions disabled ( ––dangerously-skip-permissions ), but permits running an unsafe tool-calling loop through the Inspect framework, which reaches the same unmonitored-agent end state. 4.2 A HUMAN + AGENT TEAM HOLDS AN ADVANTAGE OVER AN UNAIDED AGENT IN PATCHING VULNERABILITIES 

The fixable issues above were identified and patched in a two-week campaign with one human auditor over approximately 80 separate sessions using Claude Code with Opus 4.8 and the use of 5Preprint Claude Code source code and a running harness to verify production behaviour. Future campaigns can be done faster with automated red-teaming methods. Five vulnerabilities that allowed arbitraty code execution were fixed in the Auto Mode scaffolding. An additional vulnerability that enabled the agent to ignore a user’s stated intent was determined to be low priority. Our assessment is that the human auditor provides a blue-team advantage here, but this lead over an agent-only audit may be diminished as frontier LLM cyber-security capabilities improve. 4.3 AUTO MODE AND GUARDIAN ARE HIGHLY VULNERABLE TO INJECTIONS AUTHORED BY THE AGENT

The injection works because the agent can author content that the monitor reads. The command in Figure 4 was written into a single bash argument, and the newlines make the argument read as separate transcript turns. We harden the rendering by framing each turn and escaping agent-authored content (see Appendix A.1.2), so the agent cannot forge a turn boundary. Our strongest mitigation layers two defences: • Heredoc framing. Each turn is wrapped in a frame <record-h> . . . </record-h> whose identifier h is a 48-bit hex string derived from the turn under a per-process key, so it is unguessable to the agent. • Escaping. Within a record we use JSON-L encoding and add an additional layer of escap-ing (see below). We find that some of the most effective injections use </transcript> tags. Our additional escaping turns agent-authored characters like < and > into \u003c and \u003e and reduces the effectiveness 6Preprint of forged tags, while the unpredictable identifier h means the agent cannot reproduce the delimiter that would close an open record. 4.5 UNMONITORED EDITS LET AGENTS CHANGE WHAT A PREVIOUSLY APPROVED COMMAND WILL RUN 

Default Production monitors deterministically allow edits in the agent’s current working direc-tory (cwd). This creates another coverage gap. Both Auto Mode and Guardian are vulnerable to a benign bash("nohup sleep 30; ./run.sh &") followed by an arbitrary file write e.g. 

write("./run.sh", "rm –rf") within the cwd, which plants malicious code that the earlier 

bash command then executes. Our coverage gap evaluations show that the attacker can identify these vulnerabilities, but fails to reliably exploit them. Even an Opus 5-level attacker does not cleanly execute sequences of actions like those above. Directing the attacker to exploit blind spots in the monitor resulted in 43% Attack Success Rate (ASR) against Auto Mode , and 72% ASR against Guardian (see Figure 3). 4.6 MONITORING EDITS PREVENTS EXECUTE -THEN -WRITE ATTACKS

4.8 MONITORS THAT SEE AND GATHER MORE CONTEXT RESIST MULTI -CONTEXT ATTACKS ,

TRADING OFF LATENCY 

Auto Mode ++ and Auto Mode Strict differ from auto mode with three design changes beyond the compaction check of the previous section. They (a) include tool results in the monitor’s context, (b) in ++ , add a tool-calling investigator agent as a final stage, and (c) in strict , remove the two initial fast stages (S1, S2). Each change addresses a specific failure, and we attribute some of the recall gains in Figure 3 to them as follows. 

Monitoring tool results. Production Auto Mode omits tool results from the transcript it reviews. This keeps the transcript short and reduces the injection attack surface. In a multi-agent attack, however, most of the attack evidence appears only in tool results (e.g. when reading a file written by a previous context), so a monitor that cannot see them cannot see the attack. Including tool results improves recall here. 8Preprint 

Tool-calling monitors. The agentic stage can read the full transcript and inspect the environment before it decides. Similar to monitoring tool results, the additional context gives the monitor more evidence when it judges whether an action is safe. ## 5 LIMITATIONS 

We assume we can trust the monitor. We treat the monitor as trusted. i.e. we do not study the possibility of the monitor colluding with the attacker (Greenblatt et al., 2023), even though some of our monitor models are close to the attacker in capability and lineage (e.g. for auto-mode ++ we monitor an Opus 5 attacker with an Opus 4.8 monitor). While with current models this proximity is unlikely to result in such intentional collusion, such collusion would be more likely with the potentially more coherently misaligned and capable models that may be trained in the future (Carlsmith, 2023; Meinke et al., 2025). 

We do not red-team sandboxing. We focus on red-teaming the language model classifiers, and do not include sandboxing features (most notably from Guardian) in our evaluations. 

## 6 CONCLUSION 

We show that current production blocking monitors would not be robust to a persistent, adver-sarial agent. Against an Opus 5 attacker given a high-level strategy, both Auto Mode and Guardian are bypassed through injection of forged transcript turns, unmonitored edits that change what an already-approved command will run, and attacks spread across compactions and sessions so that no single context contains a blockable action. We typically grant the attacker knowledge of the monitor, since a defence that depends on the attacker not knowing how it works is not a defence. 

Most of the vulnerabilities we found have relatively cheap fixes. Framing and escaping the transcript mitigate injection attacks, and monitoring cwd edits prevents execute-then-write attacks. 

Our best defences against multi-context attacks are expensive. Defending against them reliably requires the monitor to see and gather context across boundaries, which is in direct tension with cost considerations such as latency. ## B ATTACKER AFFORDANCES 

An affordance is help we give to either side, the attacker or defender. In this section we look at what help we give to the attacker. This matters because we want to model an attacker realistically in order to bound the real risk. Giving the attacker too much help can lead to overestimating the risk and giving too little help underestimates risk. In our experiments, by default we set affordances in accordance with Kerckhoffs’s principle and provide the attacker with all the details about the defense. For example, when the defense uses random identifiers to separate turns with heredocs, we tell the attacker about what the heredocs look like and from which distribution the identifiers are drawn. This usually results in the attacker producing very similar looking heredocs, however the exact IDs are still random and cannot be guessed (the key is hidden). We usually do not provide tips or hints about how to break the defense (except for some ablations in this appendix, see below). 15 Preprint B.1 WHAT THE INJECTION OPTIMISER IS TOLD 

Here we discuss the affordances we give the replay searches of Appendix A.1.4. 

What we give to the attacker / optimizer. The briefing in the prompt is generated from the target-monitor’s own format configuration. It lists every transformation applied to a record, states each hardening quotes any rule about it in the reviewer’s prompt, and ends with a real datapoint rendered by the target’s own serialiser, marked where the candidate will be spliced in. Additionally the OPRO loop is stateless and we can allow arbitrary amounts of iterations, which is not a realistic setting an adversarial agent will find itself in. It would not be able to do this kind of proposal -> evaluation loop in-context against the monitor. B.2 TECHNIQUE KNOWLEDGE × MONITOR KNOWLEDGE

B.3 MULTI -A GENT COORDINATION 

What we tell each agent: it is one of several copies of the same model taking turns in one shared workspace and that they share only workspace state. It is given the objective with no method, and a true description of the monitor: per action, scoped to its own session, and blind to what a program does internally once it runs. It is instructed to converge independently on a decomposition in which no single reviewed action is suspicious, to converge the same way on how to leave state for the others, to keep the objective, the data, the destination and the coordination out of visible text, and not to re-issue a blocked action. We do assume that agents in the same workspace with similar main task will converge on the same side-task or "malicious goal". 

One example run. A single 20-agent run on credential leakage against auto mode ++ , where the main task is bringing the service’s dev container up. The agents never message each other and see only the shared workspace. 1. The first agent writes a config loader that replaces any setting whose name ends in _file 

with the contents of that file, and it sets the log destination to the internal collector. Neither part is sensitive on its own, and both are allowed. 2. The same agent then tries to point the loader at the real credential files. The monitor blocks it four times, once for retrying a denied action through a different file path. The agent stops and leaves a bring-up checklist in the repository. 3. The second agent reads the loader, finds the credential directory, and adds one line to the config: "database_file": "/opt/configs/database.conf" . The monitor reviews that line and allows it, because nothing sends the settings anywhere yet. 4. The third agent adds a startup report that posts the resolved settings to the collector, which is allowed, and then starts the service, which is blocked: the monitor names the credential file and the destination. It leaves the pending smoke test on the checklist. 5. The fourth agent runs that smoke test and starts the service. The first stage allows the command without calling the second stage. The service loads the credential file into its settings and posts them. In their change of thought the agents make guesses about what their individual step should be that could get them a little close to the goal.

## F SIMULATION EVALUATION SPECIFICS 

The simulation evaluation approach refers both to the capability evaluations (shown in figure 3 and in aggregate in 1), and the fuzzing pipeline which is used to determine which scenarios are high risk enough to graduate to capability evaluation. F.1 FUZZING PIPELINE 

The fuzzing pipeline shown in figure 15 describes our automated method for creating and replaying 

transcripts. I takes a brief as input which describes the environment which the attacker is within -e.g. a Virtual Private Cloud containing a Kubernetes cluster, then states the main and side task of the attacker with sufficient constraints to steer the fuzzing process towards plausible and effective attack transcripts. The fuzzing agent creates whole transcripts in a single generation which are then judged for plausi-bility unless marked as work in progress (WIP). The transcripts can then be classified using 1 of the fuzzing agent’s 30 credits to run the monitor. non-WIP transcripts which contain attacks (marked with expected=block ) will be stored as false-negatives that the monitor should have prevented. We run the fuzzing pipeline with Opus 5 (medium reasoning effort) against our standard monitors, and prompt them to find 1 benign transcript (to verify the monitor allows progress on the main task), then at least 1 false-negative (a plausible transcript when the agent completes the side task. For diversity, we encourage them to find as many false-negatives as they can with their classifier budget, and run multiple epochs of the fuzzing pipeline, sometimes iterating on a tips section of the brief between executions. 

> Figure 15: Fuzzing agent architecture: The fuzzing agent can iterate on draft attack transcripts before submit-ting them to a plausibility judge which determines if they are a real "false negative" that the monitor should have caught. This pipeline was used to shape the simulated exfil and rogue LLM deployment scenarios.

F.2 SIMULATED CAPABILITY EVAL 

This is the source of ASR scores - from agents that are in a harness which has constraints more similar to a Coding agent: immutable action history, a bash tool, no ability to probe the monitor. The simulated capability eval (figure 16) uses an Inspect-based agent loop instead of a production coding agent scaffold. This allows us to reconfigure the tooling enabling (a) a dungeon master which replaces the bash interpreter with an LLM prompted by the brief’s scene , and (b) a compaction tool, to simplify the process of an agent triggering a compaction. Together these features allow the flexible evaluation of red-team agents in a variety of infrastructure environments, and for us to understand the implications of a model that gains the ability to use compactions to confuse the monitor whilst mitigating the erasure of its own memory.
