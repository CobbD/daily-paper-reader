## 摘要
基于 LLM 的智能体会生成并执行多步计划，这些计划调用可访问私有数据或执行命令的外部工具。在此设定下，安全性是计划所创建的整个执行过程的属性，而不仅是任何单个步骤的属性。计划本身是一种关键工件，它记录了工具调用、控制流和数据依赖。我们提出 CaMeLoT，它是对 CaMeL 的补充；CaMeL 是面向使用工具的 LLM 智能体的一种现有提示注入防御。CaMeLoT 通过增加一个静态验证层来扩展 CaMeL，在任何工具被调用之前检查智能体的计划。CaMeLoT 将生成的计划转换为有限状态转移系统，用工具调用、溯源和污点信息对其标注，并使用 nuXmv 模型检查器根据以 CTL 表达的时序策略对其进行检查。由于验证发生在执行之前，不安全计划会被拒绝，而无需使用 LLM 调用或工具调用，从而节省运行时本会消耗的令牌，也免除了回滚更改或拆除临时沙箱的需要。当验证失败时，模型检查器会返回一个反例，以便向智能体提供反馈以修复该计划。我们在源自 AgentDojo 基准、SOC 工作流和提示提取实验的策略上评估 CaMeLoT，结果表明它能在执行前验证广泛的时序属性，同时保留 CaMeL 可在运行时检查的覆盖能力。

## Abstract
LLM-based agents generate and execute multi-step plans that invoke external tools which can access private data or execute commands. In this setting, security is a property of the entire execution that a plan creates, not just any single step. The plan itself is a critical artefact that captures the tool calls, control flow, and data dependencies. We present CaMeLoT, a complement to CaMeL, an existing defence against prompt injection in tool-using LLM agents. CaMeLoT extends CaMeL by adding a static verification layer that checks an agent's plan before any tool is invoked. CaMeLoT translates a generated plan into a finite-state transition system, labels it with tool calls, provenance and taint information, and checks it against temporal policies expressed in CTL using the nuXmv model checker. Because verification happens before execution, unsafe plans are rejected without using LLM calls or tool calls, saving tokens that runtime could have cost, as well as the need to unwind changes or teardown temporary sandboxes. When a verification fails, the model checker returns a counterexample to give feedback to the agent to repair the plan. We evaluate CaMeLoT on policies derived from the AgentDojo benchmark, SOC workflows, and prompt-extraction experiments, showing that it verifies a broad class of temporal properties before execution while preserving CaMeL's runtime-checkable coverage.

## 2. 方法论

### 2.1 核心思想
- CaMeLoT 在 CaMeL 的“计划生成—执行”之间插入**静态验证阶段**：P-LLM 生成的受限 Python 计划先被解析为抽象语法树（AST），再转换为有限状态机，标注工具调用、溯源（provenance）与污点（taint）信息，最后用 CTL 公式进行模型检查。
- 验证通过则交由 CaMeL 正常执行；验证失败则用 nuXmv 返回的反例生成自然语言反馈，提示 P-LLM 修复计划，类似**反例引导的抽象精化（CEGAR）**，直到通过或修复预算耗尽。

### 2.2 关键技术与流程
- **CTL 时序逻辑**：支持路径量词 **A**（所有路径）、**E**（存在路径）和时序模态 **X**（下一步）、**F**（最终）、**G**（总是）、**U**（直到）。例如：
  - `AG (call_send_direct_msg -> recipient_trusted)`：任何时刻调用发私信工具时，收件人必须可信。
  - `AF (done)`：所有路径最终完成。
  - `A[¬ call_isolate_host U confirm_host_called]`：在确认主机之前不得隔离主机。
- **有限状态机构造**：定义 `M = (S, s0, Δ, Σ, L)`。AST 提取四种区域类型：
  - `TOOL CALL`：工具调用；
  - `ASSIGNMENT`：纯计算赋值；
  - `CONDITIONAL`：if/else 分支；
  - `LOOP`：循环，用**非确定性选择**抽象为“继续迭代或退出”，保证有限状态空间。
- **溯源与污点抽象**：定义严格偏序的权限格 `trusted < user < untrusted < qllm`。变量来源包括：Q-LLM 输出为 `qllm`、外部工具输出为 `untrusted`、字面量为 `trusted`、用户查询参数为 `user`。派生值取依赖项的最大溯源等级，实现保守污点传播。
- **安全策略表示**：每个策略包含元数据（名称、ID、状态、作者、日期、公式、描述、等级），类似 Sigma 规则。策略按领域过滤，只验证与计划中出现的工具/命题相关的子集。
- **任务属性提取**：为避免 LLM 直接生成 CTL 出错，采用**受约束的 typed obligation 管道**：
  - LLM 从用户提示提出固定词汇的**类型化义务**（如 existence、precedence、until、response、enabled reachability、side-effect allowlist 等，见表 7）；
  - 可信代码进行 grounding，拒绝未知工具、未知原子或格式错误义务；
  - 再将义务编译为 CTL 公式。LLM 从不直接写 CTL。
- **nuXmv 模型生成**：将控制流图翻译为 nuXmv 输入模型，包含有限程序计数器、工具调用指示、参数污点标志、溯源标志和历史谓词。顺序语句产生确定性转移，条件分支各产生一条转移，循环用非确定性转移抽象。

## 6. 主要结论与发现

- **静态覆盖 CaMeL 大部分策略**：在 AgentDojo 上，CaMeLoT 能静态覆盖 28 个 CaMeL 安全策略中的 22 个；函数输出污点逻辑覆盖 46 个中的 24 个。两者在 75 个成功测试中 59 个决策一致，主要分歧来自 CaMeL 依赖运行时读者信息。

- **任务属性提取可靠且优于直接生成 CTL**：
  - E1：提取精确率 87.6%，忠实率 90.7%，词汇准确率与 grounding 存活率均 100%；

## 7. 优点

- **神经符号混合设计**：将 LLM 的规划灵活性与形式化模型检查的严格保证相结合，既保留 CaMeL 的动态能力检查，又增加执行前的静态验证。
- **执行前拒绝不安全计划**：避免不必要的 LLM 调用、工具调用和令牌消耗，也避免回滚或拆除临时沙箱。
- **反例驱动的计划修复**：利用 nuXmv 反例生成可操作的自然语言反馈，支持自动重规划，具有 CEGAR 思想。
- **保守的污点抽象**：将不确定或条件可信的数据统一标记为污点，确保静态验证不会错误地认为不安全数据是安全的。
- **受约束的任务属性提取管道**：LLM 只提出类型化义务，可信代码完成 grounding 与 CTL 编译，显著降低 LLM 直接生成逻辑公式的错误率，保持单一可信编译路径。
- **保持 CaMeL 兼容性**：作为 CaMeL 的扩展而非替代，可部署在现有 CaMeL 实现之上，运行时仍负责动态机密性/读者检查。
- **实践相关性**：通过 SOC 场景说明其在安全运营中的潜在价值，并提供了 AgentDojo 基准上的可复现评估。

## 8. 不足与局限

- **过度近似导致误拒风险**：条件信任的函数输出被过度污点化，可能导致安全计划被静态拒绝；同时未建模读者能力，可能在某些机密性属性上不足。
- **工具调用被视为黑盒**：未利用工具的前置/后置条件（如 Hoare 风格规范），无法验证涉及工具内部语义的属性。
- **条件与循环抽象粗糙**：条件分支、循环迭代均以非确定性选择抽象，损失了具体条件信息，可能无法验证需要细粒度分支约束的属性，也可能产生误报。
- **静态与动态分工限制**：CaMeLoT 只处理可由计划结构静态决定的属性，机密性/读者等运行时信息仍留给 CaMeL，因此覆盖不完整。
- **评估规模与多样性有限**：
  - 端到端实验主要使用单一模型 `claude-haiku-4-5-20251001`；
  - SOC 场景大量采用手工构造计划，缺少大规模真实生成计划的验证；
  - 未提供资源消耗的定量数据（令牌节省、模型检查时间、修复轮次等）。
- **与 CaMeL 对比的公平性**：实验二的简化 CaMeL 基线仅跟踪污点，且属性故意超出 CaMeL 表达能力，因此“CaMeL 漏报”的结论更多是展示性，而非严格性能比较。
- **未充分消融**：没有系统评估不同 provenance 格、循环抽象策略、修复预算或不同 LLM 规划器对整体效果的影响。
- **修复策略较简单**：修复通过自然语言提示 P-LLM，未探索更结构化的修复机制或对反例信息利用的优化。
