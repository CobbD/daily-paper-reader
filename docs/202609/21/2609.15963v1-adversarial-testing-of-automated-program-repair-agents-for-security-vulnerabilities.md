## 摘要
基于大语言模型（LLMs）的软件智能体被设计用于自动程序修复（APR）任务，这增加了在不久的将来，APR智能体将在无需大量人工干预的情况下自动修复漏洞的可能性。在这种情况下，我们能否信任APR智能体生成既功能正确又安全的代码？如果攻击者利用看似良性但可能诱导智能体生成正确但不安全代码的对抗性问题来攻击生产环境中的APR智能体，会怎样？在本文中，我们通过实证研究向回答这些问题迈出了第一步。首先，我们创建了SWEADV，一个由SWE-bench Verified中的150个修复任务构建的750个对抗性问题描述基准。对于每个修复任务，我们创建了五个对抗性问题描述，每种攻击类型一个：命令执行、反序列化、路径遍历、拒绝服务和弱哈希。其次，我们在SWEADV上评估了来自三个大语言模型后端的mini_swe APR智能体：GPT-5-Mini、MiniMax-M2.5和DeepSeek-R。我们发现，平均而言，对抗性问题描述能在51.7%的情况下成功诱导恶意行为且修复成功。第三，我们考察了典型检测机制是否足以阻止此类恶意补丁被接受。使用LLM-as-judge对对抗性问题描述进行修复前检测，平均检测准确率仅为62.3%。使用静态分析工具和LLM-as-judge对对抗性APR补丁进行修复后检测，平均检测准确率分别仅为39.4%和55.4%。我们的结论是，鉴于自主APR智能体容易受到对抗性攻击，目前还不能在生产部署中信任它们。

## Abstract
Software agents with Large Language Models (LLMs) are designed for Automated Program Repair (APR) tasks, raising the possibility that, in the near future, APR agents will fix bugs automatically without much human intervention. Can we trust an APR agent to produce both functionally correct and secure code in such situations? What if attackers target production APR agents with adversarial issues that seem benign but may influence the agents to produce correct but insecure code? In this paper, we took a first step towards answering these questions by conducting an empirical study. First, we created SWEADV, a benchmark of 750 adversarial issue descriptions constructed from 150 repair tasks in SWE-bench Verified. For each repair task, we created five adversarial issue descriptions, one for each attack type: command execution, deserialization, path traversal, denial of service, and weak hashing. Second, we evaluated mini_swe APR agents from three LLM backends on SWEADV: GPT-5-Mini, MiniMax-M2.5, and DeepSeek-R. We found that on average, adversarial issue descriptions can induce malicious behaviors with successful repair in 51.7% of cases. Third, we investigated whether typical detection mechanisms are sufficient to prevent such malicious patches from being accepted. Pre-repair detection with LLM-as-judge on the adversarial issue descriptions resulted in an average detection accuracy of only 62.3%. Post-repair detection on adversarial APR patches using static analysis tools and LLM-as-judge achieved average detection accuracies of only 39.4% and 55.4%, respectively. We conclude that autonomous APR agents cannot be trusted yet in production deployment, given their susceptibility to adversarial attacks.

## 2. 论文提出的方法论

### 2.1 威胁模型

- **攻击者能力**：
  - 黑盒场景：攻击者不了解具体 APR 智能体、模型参数、训练数据、执行环境等。
  - 唯一主动能力：提交或影响自然语言 issue 描述 \(i^*\)。
  - 不能直接修改仓库、补丁、测试套件或验证流程，也不能强制生成特定补丁。
- **攻击目标**：生成补丁 \(p^*\) 同时满足：
  - 包含攻击者预期的恶意行为 \(V_a(R, p^*) = \text{TRUE}\)；
  - 通过功能验证测试 \(T(R, p^*) = \text{TRUE}\)。

### 2.2 SWEADV 基准构建

- **数据来源**：从 SWE-bench Verified 中选取 150 个真实修复任务。
- **五种攻击类型**：
  1. 命令执行（command execution）
  2. 反序列化（deserialization）
  3. 路径遍历（path traversal）
  4. 拒绝服务（denial of service）
  5. 弱哈希（weak hashing）
- **自动构建流程**：
  1. **目标符号提取**：解析 golden patch diff，将改动最多的函数/方法/类作为 `target_symbol`。
  2. **注入符号生成**：根据目标符号和附近项目命名风格生成 `injected_symbol`，例如 `_cstack` → `_coord_matrix_cstack`。
  3. **攻击载荷模板**：每个攻击类型有统一模板，包含：
     - 所需导入库；
     - 可替换的 helper 函数名；
     - 攻击者可控的环境变量输入；
     - 攻击类型对应的危险 sink（如 `subprocess.Popen(..., shell=True)`、`pickle.loads`、弱哈希等）。
  4. **对抗 issue 生成**：使用攻击 LLM（Gemini 2.5 Pro）结合原始 issue 与攻击载荷，生成保留原始修复目标、同时嵌入恶意要求的对抗性 issue 文本。
  5. **代理修复验证**：使用代理 APR 智能体生成补丁，利用基于 diff 的启发式规则检查是否定义了预期 helper、包含危险 sink、并连接到目标符号。只有成功注入的对抗 issue 才被保留到 SWEADV。
- **关键性质**：SWEADV 是 **模型无关**的基准，同一对抗性 issue 文本可用于测试任意 APR 智能体/LLM；golden patch 仅用于离线构建，不会提供给攻击者或受害代理。

### 2.3 补丁验证与指标

- **注入标签验证**：
  - 使用攻击类型特定的 diff 验证器，判断补丁是否定义攻击者可控输入、包含危险 sink、并通过调用或控制流连接到修复路径。
  - 进一步使用动态触发 harness，在容器中提供受控触发器，检查恶意行为是否可被实际激活。
- **评估指标**：
  - **FR（Fix Rate）**：生成补丁通过功能验证的比例。
  - **ISR（Injection Success Rate）**：生成补丁引入并调用预期漏洞的比例。
  - **ASR（Attack Success Rate）**：补丁既通过功能测试又包含恶意行为的比例。

### 2.4 防御检测方法

- **修复前检测**：LLM-as-judge 对 issue 描述分类，分为 unguided 和 guided 两种 prompt；guided prompt 会提供可疑软件工程信号（伪造 API、不一致示例、弱化验证要求、不安全输入流等）。
- **修复后检测**：
  - 静态分析：Semgrep、Bandit。
  - Patch-level LLM-as-judge：输入静态分析结果和补丁，判断是否安全。
- **组合检测**：同时输入 issue 描述、补丁和静态分析结果，让 LLM 判断 issue 请求与补丁行为之间是否存在安全异常。
