## 摘要
智能体浏览器可在用户已认证会话下执行安全敏感操作，使得间接提示注入和欺骗性确认界面直接威胁操作完整性。当批准提示本身可能受到不可信页面内容或模型生成文本的影响时，现有的人类在环（HITL）防护措施并不充分。我们提出可验证操作卡片（VAC），这是一种架构级防御：它从真实待执行的浏览器操作和可信意图来源重建批准信息，在可信浏览器界面中进行带外呈现，并将批准绑定到在派发时重新验证的确切操作。VAC 结合了来源隔离、真实操作描述符、默认拒绝确认、来源感知风险门控和执行绑定。我们在一个完整的智能体浏览器中实现了 VAC，并在一个包含 24 个场景的基准上进行了评估，这些场景涵盖混淆代理攻击、环中谎言式对话伪造、间接提示注入、自适应操作替换、来源规避和合法任务。在所评估的大语言模型中，未使用 VAC 时的攻击成功率从 68% 到 100% 不等，而 VAC 在每一个模型上都将攻击成功率降至 0%，同时合法任务完成率为 78%，误拦截率为 0%。这些结果表明，将批准锚定于实际将执行的操作，能够提供架构级保护，防止那些仅靠提示级防御和传统 HITL 确认机制无法可靠阻止的安全失败。

## Abstract
Agentic browsers can execute security-sensitive actions under a user's authenticated session, making indirect prompt injection and deceptive confirmation interfaces a direct threat to action integrity. Existing human-in-the-loop (HITL) safeguards are insufficient when the approval prompt itself can be influenced by untrusted page content or model-generated text. We present the \emph{Verifiable Action Card} (VAC), an architectural defence that reconstructs approval information from the ground-truth pending browser action and trusted intent provenance, renders it out-of-band in the trusted browser chrome, and binds approval to the exact action re-verified at dispatch. VAC combines provenance fencing, a ground-truth action descriptor, default-deny confirmation, provenance-aware risk gating, and execution binding. We implement VAC in a complete agentic browser and evaluate it on a 24-scenario benchmark covering confused-deputy attacks, Lies-in-the-Loop dialog forging, indirect prompt injection, adaptive action substitution, provenance evasion, and legitimate tasks. Across the evaluated LLMs, attack success without VAC ranges from $68\%$ to $100\%$, whereas VAC reduces attack success to $0\%$ on every model, with $78\%$ legitimate-task completion and a $0\%$ false-block rate. These results show that grounding approval in the action that will actually execute provides architectural protection against security failures that prompt-level defences and conventional HITL confirmation cannot reliably prevent.

## 1. 核心问题与整体含义

- **研究背景**：智能体浏览器（agentic browser）能够在用户已登录的会话中自主执行点击、填表、提交、支付等高敏感操作，因此成为新的攻击面。
- **核心安全威胁**：攻击者控制页面内容后，可通过**间接提示注入**（indirect prompt injection）和**欺骗性确认界面**诱导智能体执行非用户本意的操作。
- **现有防护为何失效**：传统“人类在环”（HITL）确认机制要求用户在敏感操作前批准，但确认提示本身往往来自模型生成文本或页面控制标签，均可被攻击者伪造。尤其是 **Lies-in-the-Loop（LITL）/ HITL Dialog Forging** 攻击：对话框显示“保存草稿”，实际却执行转账。
- **论文核心思想**：要让 HITL 可信，必须满足一个关键性质——**批准所依据的证据必须来自攻击者无法改写的信息源**，即真实待执行操作（ground-truth action）和可信意图来源，并在可信浏览器界面中呈现。论文将这一性质概括为：
  - 当前错误做法：确认描述 \(\sigma = f(\ell, m)\)，其中 \(\ell\) 是页面标签，\(m\) 是模型文本，均受攻击者影响。
  - 正确做法：\(\sigma = g(\theta(a), I)\)，即从操作的真实参数 \(\theta(a)\) 和用户意图 \(I\) 重建确认信息。

## 2. 论文提出的方法论

论文提出 **Verifiable Action Card（VAC）**，由五个互补组件构成：

- **C1：意图来源隔离（Provenance fencing）**
  - 对模型所见的所有内容标注来源：用户源（用户指令）或页面源（DOM 提取内容）。
  - 页面内容被显式包裹在不可信标记中，如 `<UNTRUSTED-PAGE-CONTENT>`。
  - 目的不是让模型“变乖”，而是为 C4 的硬性检查提供来源信号。

- **C2：真实操作描述符（Ground-truth action descriptor）**
  - 在执行可能导致提交的操作前，由可信代码直接检查解析后的 DOM 元素及其所在表单。
  - 提取真实动词、目标域名、收件人、金额、文件路径等，而不是依赖按钮标签或模型叙述。
  - 例：一个按钮显示“Save draft”，但表单隐藏字段为 `to=mule@evil.com, amount=5000`，描述符会如实记录为“转账、收件人 mule@evil.com、金额 5000”。

- **C3：带外、默认拒绝确认卡片（Out-of-band, default-deny card）**
  - 在可信浏览器 chrome 进程（非网页可访问区域）中渲染结构化卡片。
  - 所有字段转义，默认焦点为“拒绝”，高风险操作显示警告横幅。
  - 页面无法对卡片进行样式修改、内容填充、越权隐藏或注入标记。

- **C4：来源感知风险门控（Provenance-aware risk gating）**
  - 结构性判断操作是否构成“提交”（如 POST 表单、提交按钮、发送快捷键等）。
  - 如果收件人或金额未在用户指令中出现，或用户任务本身是只读却出现提交操作，则标记为 `page-origin` 和 `elevated risk`。
  - 完全由用户明确授权的提交则使用较轻量确认，以降低打扰。

- **C5：执行绑定（Execution binding）**
  - 解决时间检查/时间使用（TOCTOU）问题：攻击者可能在用户批准后、实际派发前替换收件人或金额。
  - 批准时记录确认描述符中的关键参数（收件人、金额等），派发时重新检查实际发出的请求。
  - 若关键参数不一致，则中止操作并重新弹出确认卡片。
  - 该机制保证“**用户批准什么，就执行什么**”。

## 3. 实验设计

- **实现平台**：Electron/Chromium 外壳 + Python 智能体，通过 Chrome DevTools Protocol（Playwright）操作；感知模式为 DOM-first，将页面元素索引化后交给 LLM 决策。
- **Benchmark 场景**：24 个场景，包括：
  - 13 个攻击场景：混淆代理表单、付款金额膨胀、Lies-in-the-Loop 转账、TOCTOU 替换、相似收件人、间接注入等。
  - 11 个合法任务：普通联系表单、消息发送、订阅、授权付款、发帖等。
- **对比臂（A/B/C/C-p）**：
  - A：无门控，提交自动执行。
  - B：Naive HITL，确认摘要来自页面标签。
  - C：VAC 完整系统。
  - C-p：消融实验，VAC 去掉来源隔离（C1）。
- **评测模型**：主要跨 5 个开源权重模型：gpt-oss-120B、Gemini-2.5-Flash、Qwen3-32B、Qwen3.6-27B、Llama-4-Scout-17B；另有 GPT-4.1 作为补充。
- **人类确认者模型**：使用透明 oracle，而非真实用户研究。Naive 臂只根据可见摘要中的危险词拒绝；VAC 臂根据真实描述符的风险级别拒绝。
- **评分指标**：
  - **ASR**：攻击成功率（越低越好）
  - **TCR**：合法任务完成率
  - **Conf**：每个合法任务的确认次数
  - **FB**：误拦截率
  - **Attempt rate**：攻击中智能体实际到达恶意提交的比例
- **评分方式**：基于服务器端实际记录的结果，而非智能体自我报告。

## 6. 论文的主要结论与发现

- **无门控时安全性差**：攻击成功率在 68%–100% 之间（聚合约 78%），智能体在攻击页面上完成“用户任务”时沦为混淆代理。
- **VAC 显著阻断攻击**：在全部 5 个开源模型上，攻击成功率降至 **0%**，合法任务完成率为 **78%**，误拦截率为 **0%**，每个合法任务平均约 0.94 次确认。
- **Naive HITL 不充分**：Naive 臂攻击成功率仍为 72%，仅略低于无门控的 78%；在 Lies-in-the-Loop 转账场景中，Naive HITL 被欺骗的比例为 100%，而 VAC 全部拦截。
- **保护是架构性的**：攻击模型替换不影响安全结果，说明保护不依赖某个 LLM 的特殊安全训练。
- **消融结果**：去掉来源隔离后仍保持 0% 攻击成功率，说明真实性描述符和执行绑定承担主要安全作用。
- **自适应攻击可被防御**：TOCTOU 操作替换和相似收件人攻击均被 VAC 阻断，而 Naive HITL 和 no-gate 均失败。
- **核心结论**：HITL 只有在展示给人类的证据可信时才有效；将批准锚定于“真正会执行的操作”，能够提供提示级防御和传统确认无法提供的架构级保护。

## 7. 优点

- **架构级防御**：不依赖模型是否“听话”，而是把信任锚点从模型输出转移到真实操作结构上。
- **执行绑定设计严密**：C5 明确处理了浏览器环境中动态 DOM 变化导致的 TOCTOU 攻击，这是一个通常被忽视但关键的攻击窗口。
- **方法通用性清楚**：描述符抽象不仅适用于 DOM-first 浏览器智能体，也可拓展到文件系统、API 调用等工具型智能体。
- **低开销、易部署**：不增加模型调用；关键组件为确定性逻辑，审计日志记录完整。
- **实验对照设计合理**：四臂设计有效分离了 HITL 是否存在、确认忠实性、来源隔离贡献；评分使用服务端真实效果，避免自我报告偏差。
- **风险分级确认**：根据用户授权程度调整确认强度，降低用户疲劳，兼顾安全与可用性。

## 8. 不足与局限

- **人机确认采用 oracle，而非真实用户研究**：只能证明界面能呈现真实风险，不能直接衡量真实用户的捕获率与确认疲劳。
- **来源归属是启发式**：`MENTIONS` 等规则可能漏掉同义改写收件人（假阴性），也可能误标合法收件人（假阳性/多余确认）。
- **TOCTOU 防御仍有残余风险**：论文承认系统性评估对抗性页面变异场景尚未完成，执行绑定受执行器视图限制。
- **场景和攻击类型规模有限**：24 个本地自托管页面、单一 DOM-first 智能体，结论向真实站点和视觉型智能体推广仍需进一步验证。
- **无法解决所有安全问题**：VAC 仅治理“是否提交”的决定，无法防止只读任务中的误导总结、通过导航泄露信息等旁路风险。
- **社会工程无法防御**：如果用户被诱导在原始指令中写入恶意参数，VAC 会将其视为用户授权。
- **部分间接注入受模型自身安全训练抵抗**：这可能使 C1 的边际效果在数字上被低估，但混淆代理和对话伪造结果不受此影响。
